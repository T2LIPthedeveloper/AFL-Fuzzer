Date: 2026-08-26. Scope: Spring Boot rebuild. Language: STE-100 style. Short sentences. Active voice. Simple words.

Greptile Copilot Human-in-the-loop

Note: In this report, Copilot means Cursor Bugbot. GitHub Copilot did not run. This report does not use a “no review” baseline.

1. Purpose

This study compares three review methods on a Spring Boot fuzzer service.

The service lives in spring-fuzzer/.

The study uses three additive pull requests against main-spring.

3. What the service does

main-spring adds a Spring Boot microservice.

The service starts fuzz campaigns through REST.

Package boundaries are api, campaign, mutation, targetclient, model, and config.

Maven tests passed on all three develop branches.

4. Code changes by tier

4.1 Small

The small tier adds dictionary insert and splice.

The small tier adds crash-hot mutation intensity.

The small tier resolves resume paths to absolute paths.

4.2 Medium

The medium tier adds PowerScheduleService.

The medium tier adds DeviceEnergyScheduler and a device campaign API.

The medium tier loads an HTTP dictionary file.

4.3 Large

The large tier adds corpus, coverage, crash triage, stats, havoc, minimizer, and HTML reports.

The large tier wires these parts into CampaignService.

6. Results by tier

6.1 Small — PR #4

Greptile confidence: 2/5.

Greptile understood the change set.

Greptile found mutation bound risk, unsafe shared strategy map use, and a splice no-op path.

Copilot: No separate small-tier Bugbot pass is required for the final matrix. The small tier is mostly clean feature work.

Human: A careful human can approve after a bound check. A human may miss concurrent map risk under time pressure.

6.2 Medium — PR #5

Greptile confidence: 0/5.

Greptile understood the scheduling work.

Greptile found disconnected feedback paths.

Greptile found dictionary load failure in a packaged JAR.

Greptile found schedule key collision across endpoints.

Greptile found an unbounded device-campaign request risk.

Copilot also found the missing device record call and the fixed zero coverage gain path.

Human: A careful human likely finds the missing record call. A human may miss the JAR dictionary path and the unbounded rounds risk.

8. Did Greptile understand the work?

Yes. Greptile stated the intent of each tier.

Greptile focused on integration seams in the Spring service.

Greptile used graph-style reasoning for missing feedback edges.

Greptile posted flowcharts on all three PRs.

Greptile did not show TREX runtime proof on these PRs.

9. Pros and cons

ReviewerProsCons
GreptileAlways on. Strong integration finds. Confidence score. Flowcharts. Security note on unbounded work.Paid service. Can miss some parent/child key details. No TREX proof here.
CopilotStrong defect recall on the large tier. Finds wiring bugs across services.Not always on GitHub in this setup. No confidence score. Needs a manual run.
Human-in-the-loopOwns merge judgment. Can test runtime behavior. Can judge API design.Slow. Uneven under large diffs. Misses some orphans when rushed.

10. Recommendation

Use a human reviewer on every merge to main-spring.

Add Greptile or Copilot as a second pass.

Prefer Greptile when you need unattended GitHub notes and clear confidence scores.

Prefer Copilot when Cursor review is already part of the daily workflow.

Do not merge PRs #5 or #6 until the high-severity wiring defects are fixed.
